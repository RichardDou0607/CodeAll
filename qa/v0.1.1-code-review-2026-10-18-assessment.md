## 2. 逐条核验

### 2.1 Standards 轴

**S1（报告:20-26）——事实成立，定性需降级，修复范围不全。**
- 成立部分：docs/26:11「现回退 UI 粘贴」、docs/26:33 SPIKE-4②「UI 粘贴通道加固」，与 docs/40 §3.12/§3.14（:502、:541-544）及 demo/README:101-104 的「当前接线不会回落 UI 粘贴 / 既有死代码」直接冲突；`adapters/cli-control.mjs` 对 ZCode 无条件先走 app-server 管道，UI 回落分支不可达。矛盾真实存在，应改。
- 需修正：①「硬违规」缺少可引仓库编码规范——仓库根无 AGENTS.md / CONTRIBUTING.md / CODING_STANDARDS.md，亦无 lint/包管理配置；该问题本质是**文档一致性缺陷（高优先级）**，不是 Standards 轴意义上的「代码违反文档化规范」。②「反向漂移」不成立：文件 mtime 显示 docs/26（10-17 11:57）早于 docs/40（10-17 19:23）与 demo/README（10-17 19:06），属**纠偏后未同步更新的陈旧表述**。③修复范围漏 docs/26:52 风险表「沿用 ZCode UI 通道既有模式」，只改 §1 表格行与 SPIKE-4 清不干净。
- 判定：**事实成立 / 定性降级 / 修复位置补全**。

**S2（:28-32）——成立（措辞略强）。** `demo/test-env.mjs:17` 导出 isolatedEnv；`scripts/perf-baseline.mjs:31-32` 与 `scripts/perf-verify.mjs:80-81` 各有一份逐字相同的 DSH_SCRUB + isolatedEnv（报告以常量行作块引用，函数在下一行，可接受）。严格说并非「三份同形」：test-env 版无 TMPDIR 隔离、无绝对路径校验，收敛时需把这两点并入共享 helper。`perf-baseline.mjs:21` 跨目录 import `demo/test-model-fixture.mjs` 属实，复用通道成立。

**S3（:34-38）——成立。** `adapters/zcode-adapter.mjs:328` slowDown 与 :380 pump 尾部同写 `Math.min(backoffMs * 2, 10_000)`，语义一致，行号精确。

**S4（:40-44）——成立。** `demo/framed.mjs:270/284/295` 三个 `{at,data,key}` + TTL + stableJson 缓存形状，行号精确。标签「Duplicated Code / Data Clumps」中 Data Clumps 可商榷（本质是重复的缓存样板），不影响建议。

**S5（:46-50）——论据不成立，建议撤销或降级为「可选死代码清理」。**
- 报告称 `demo/window.html:1033` 的 `now − elapsedMs` 回退「引入渲染端本地时钟推算、与契约擦边」。
- 实查：window.html:822 `const now=snap.ts||Date.now()`，`now` 是 Hub 快照 `ts`；`elapsedMs` 也是 Hub 字段。该回退是**同一 Hub 帧内两字段相减**，不是本地时钟推算；docs/51 §3.2 T2 明许「缺失时回退 snapshot.ts − session.since（同帧两字段相减，仍**不读本地时钟**）」。
- 契约 §5.3 中 `sessions[].since` 是基础必填字段，`snapshot()` 始终输出 since（framed.mjs:559；初值 :406/:411、变更 :424），故回退实际不可达；tick 路径用 Hub 的 `tick.ts`（window.html:1536-1558），同样不是本地钟。
- 报告引「契约 §8.2」是仓库既有简写（docs/51 同用），但原句是「工作框不做任何时间推断」，与报告转述「渲染层不做无状态推断」有出入。
- 结论：删除该死回退可作为**可选清理**保留建议，但不应作为「契约擦边」判断题，也不应计入 Standards 轴「嗅觉」（它不是 Fowler 嗅觉）。

### 2.2 Spec 轴

**P1（:56-64）——成立（核心判断正确），但修复范围不完整。**
- 证据核实：`scripts/perf-verify.mjs:295-318` 仅 1MB/8MB 两档、阈值 `<1MB`；附录 C 的 P2-diff 也只写 8MB 实测与「旧实现 ≈200MB」；docs/25:38 确实写「>50MB 独立测量 0 B vs 旧 ~2.64GB（附录 C）」；qa/perf 九个 JSON 语料均为 1.1MiB，无 >50MB 产物。**P1 主体成立。**
- 但同一说法还出现在 docs/25:63（量化口径「直接测量：>50MB…」）、docs/25:105（锚点「应 ≈0」）、CHANGELOG:14/44；报告修整只提 :38/附录 C，应同步清理这些位置（:105 为「应」的估算锚点，可明确标注估算）。
- 补测口径问题：只测新代码的 >50MB 档无法证明「旧实现约 2.64GB」；要么用 `git worktree`（HEAD=f577807）对照旧码实测，要么把该数字降级为估算。
- 附加遗漏：PERF-2 完成条件（docs/25:38）要求「乱序/坏帧/半帧/轮转」合成断言，而 perf-verify P2-correct（:320-353）仅覆盖半帧 + 轮转；「乱序/坏帧」无断言，报告未指出该证据缺口。

**P2（:65-68）——事实成立，清单不完整。**
- V01–V06 修正后实机回归、包重建、`--live` 未做属实（docs/25:68、qa/v0.1.1-acceptance-2026-10-17.md:88-90 标 ⏳）。
- 漏项：① docs/25:62 验收门槛与 acceptance:90 明确「非 `--live` 的 multi-source-check」也未执行；② docs/25:136「带插件的实机复测」仍待做（部署口径目前只有标准档近似）。报告只列 `--live`。定性「无需改代码/按清单执行」正确。

**P3（:69-73）——核心成立，引用位置不精确。**
- 机制核实：目录缓存 TTL 只在 `snapshot()` 中惰性判断（framed.mjs:272、:468-470），静默可见实际由 15s 四态轮询（:1487）+ 5s WORKSPACE_STORE mtime（:1491）+ 2s 节拍（:1492）驱动；P4-a 用例名「目录 TTL 15s」（perf-verify:266）确与机制不符。核心成立。
- 但「15s TTL + 2s 节拍」短语只出现在 docs/25:40；docs/25:59 已是「四态 mtime + WORKSPACE_STORE mtime 5s 静默信号 + 15s TTL 兜底」，本身不误。调整目标应为 **:40 + perf-verify 检查名**，不必把 :59 一并列入。

**通过项（:80-85）——数字大体属实，两处标签/范围有误。**
- 吻合项：after-pure-fixed 纯空闲 CPU 190 ms/分钟、SSE 270,932 B、标准档 idle 536、active 617、boot 618ms、idle readBytes 0B/0ops；pre 1080/1170 ms、SSE 4,753,983/4,754,373；−82.4%/−83.8%、−94.3%。test-tick 11/11 已实跑复现。
- 错误：①「空闲 SSE 190ms/270,932B」——190ms 是 CPU，不是 SSE；②「标准档 idle 536/617」——536 是 idle、617 是 active；③「九个 JSON 均与附录 B/C 吻合」说过头：after-run1/2 未被附录引用（其 727/795 对应首轮 CHANGELOG 口径），实际入册/声明的是 7 个；④未提 PERF-2「乱序/坏帧」断言缺口（见 P1）。

**越界项（:75-78）——成立。** docs/25:14 明示「不吸收 docs/26 的桌面端攻坚」；README/docs/22/23/24 仅为排期联动文字；demo/mini.html 的 tick 适配由 test-tick T5 覆盖，属 PERF-1 完成条件的必要收口。判可接受合理。

**总体结论（「无阻塞性产品缺陷」）**：本次抽检范围内未发现反证；但报告只实跑 test-tick，未复跑全套与 perf-verify，也未做 >50MB/旧码对照，该结论应保留「基于静态审查 + 既有验收记录」的限定。
