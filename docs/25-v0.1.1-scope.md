## 3. 性能优化任务（依据 2026-10-17 开销分析）

开销根因（分析结论摘要）：① `broadcast()` 每 2s 全量重建 snapshot + 大 payload 双客户端推送；② DSH 日志跟随器 800ms 定时 + fs.watch 双触发**整文件** `readFileSync`；③ 用量扫描 60s 周期、变更文件整文件重读；④ 各路固定轮询（目录缓存 5s、agent 四态 3s、ZCode sqlite 1.5s、Claude/Codex/Kimi 跟随**各 1.2s**）；⑤ 每次投递 spawn 独立 agent 进程（200MB+ 级、无并发上限、存活至回合结束）。

## 4. 验证纪律与验收

- 默认只跑隔离测试（mock CLI、合成日志、假插件），不消耗真实模型额度；真实闭环须用户明确授权。
- **隔离纪律（二轮补强）**：所有起 framed 服务的脚本/测试必须显式隔离 DSH 根路径——清 `DSH_HOME`/`DSH_SESSIONS`/`DSH_WORKSPACES`/`DSH_SESSION_ID`/`DSH_PROFILE*`（或指向临时 home），否则会跟随真实用户 ~/.dsh 日志，产生假故障并污染数字。首轮审查实测：未清 `DSH_*` 时 perf-verify 出现 3 项假失败、P1-a 数字失真；清后首轮 12/12、终轮 **13/13** 且与附录 C 一致。`scripts/perf-verify.mjs` / `scripts/perf-baseline.mjs` 与相关测试已改用隔离 helper。
- **延迟 tradeoff 登记（二轮修订；替代原「UI 端到端状态延迟不劣于 v0.1.0」的一刀切口径）**：

| 信号 | 最坏端到端延迟 | 依据 |
|---|---|---|
| DSH 日志跟随事件 → SSE 全量推送 | **~505～527ms**（终轮 P1-b① 实测 **506ms**：500ms 去抖 + 处理/推送） | PERF-2 fs.watch 500ms 去抖 + 事件即时 broadcast（脏冲刷） |
| DSH 插件进程内事件 → SSE | 即时（无文件跟随；事件到达即 broadcast） | 插件通道 |
| ZCode sqlite 新行（空闲退避档） | **≤10s**（退避封顶；取到新行后回 2s 基准） | PERF-4 指数退避 |
| agent 四态（软件运行/安装状态） | **≤17s** | 15s 轮询 + 2s 节拍 |
| 目录/工作区会话变化（无事件源时） | **≤~17s**（终轮实测：新 claude 会话经 SSE-only **11.0s** 可见；workspace.json title 静默改写 **1.7s**；四态 mtime + `WORKSPACE_STORE` mtime 5s 静态信号 + 15s TTL 兜底）——极端情况（不改任何被探测 mtime）的无限滞留由 v0.1.2 分钟兜底封顶 ≤~62s（见 [docs/27](./27-v0.1.2-scope.md)） | PERF-4 静默变化驱动 |
| 用量（Token/日历） | 打开用量视图时（≥60s 陈旧）或启动 +5min；非实时——空闲滞留与重启全量由 v0.1.2 分钟兜底 + PERF-7 四级增量解决（见 [docs/27](./27-v0.1.2-scope.md)） | PERF-3 懒触发 |
